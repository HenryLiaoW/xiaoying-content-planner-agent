# 复盘

| 项目 | 内容 |
|---|---|
| 主要取舍 | 手写决策循环 + SQLite；脚本用确定性模板；预算与截止时间各自硬约束；finish 是会失败的工具 |
| 最难的点 | 分清"模型决策"与"代码守约束"的边界：既不能写死"超预算就换档"（那不是 Agent），也不能让模型自己算账（数字会错）。解法：估算与拒绝由代码做，改什么由模型选，拒绝原因作为观察回传 |
| 已完成 | 11 个离线场景、80 项测试；真实模型 6 组路径（正常、失败一次重试、持续失败主动停止、预算紧、截止时间紧后重规划、中断后续跑，见 03）；重复执行幂等；调整说明、面向运营的结论与转交说明；五要素 trace |
| 已知不足 | 每个真实场景只跑了一次，没有统计稳定性；真实模型在预算约束下没有走到"估算后重规划"（只在截止时间约束下走到）；持续故障下模型最初不会主动停，补了累计失败信息后复测一次才停，无法区分是提示还是重试上限起的作用；`handoff_note` 与"动作额度提前提醒"是最后加的，只有离线验证；`llm` 脚本后端未实现（接口已留），脚本正文是模板拼的；素材匹配是关键词打分；单进程单用户；失败不计费是简化假设 |
| 下一步 | `llm` 脚本后端 + 引用校验；联网素材源作为第二数据源；HTTP 包装；评测集（多次运行统计重规划发生率与 token 成本） |
| 下一轮验证 | 同一输入跑 N 次统计状态分布与费用；注入不同位置的失败看保留率；对比 template 与 llm 后端的素材引用准确率 |

实际用时与未完成部分见 `docs/timelog.md`。不把"计划做"写成"已实现"。
