# 复盘

| 项目 | 内容 |
|---|---|
| 主要取舍 | 手写决策循环 + SQLite；脚本用确定性模板；预算与截止时间各自硬约束；finish 是会失败的工具 |
| 最难的点 | 分清"模型决策"与"代码守约束"的边界：既不能写死"超预算就换档"（那不是 Agent），也不能让模型自己算账（数字会错）。解法：估算与拒绝由代码做，改什么由模型选，拒绝原因作为观察回传 |
| 已完成 | 11 个离线场景、92 项测试；真实模型记录覆盖正常、失败一次后重试、持续失败后主动停止、预算紧、截止时间紧后重规划、中断后续跑（见 03）；最终候选源码上的两轮真实复验（独立数据库、记录源码版本、不覆盖历史输出）；重复执行幂等；真实与离线记录分库且不混用；调整说明、面向运营的结论与转交说明；五要素 trace；终报记录源码版本 |
| 已知不足 | **真实模型没有复现参考实例的"超预算后再改"**：价格表写在提示词里，模型拟计划时就算好了，只在截止时间约束下出现过"估算不通过再改"；**缺少跨档位的提前停止策略**：换档位会重置重试次数，持续故障时靠累计失败提示与动作上限收场，改进后三次真实运行分别在 4、4、3 次失败后停止，用了 10、15、10 次动作；**缺少重复运行统计**：同一场景只有两三次真实记录，走向不完全相同；模型有时发出不合法的工具参数（11-11 的 10 次真实运行里有 4 次），现在靠重发恢复，每次多用 1 次动作额度；提示词里的决策指引写得较具体，模型的选择空间有限；trace 里的"决策依据"是模型自述，出现过与实际动作不一致的情况；脚本正文由模板生成、素材匹配是关键词打分，方案内容单薄；降级前不询问运营，故障恢复后续跑不会自动恢复档位；多次约束调整时，给运营的话只描述第一次调整（完整记录在 `adjustments`）；命令行原型，单进程单用户；失败不计费是简化假设 |
| 下一步 | 跨档位的提前停止策略（按工具累计失败设上限或退避）；重复运行统计；不在提示词里给价格、只靠估算工具获知费用时的重规划表现（已暂缓，未做）；`llm` 脚本后端 + 引用校验；降级前先询问运营；联网素材源作为第二数据源；HTTP 包装与界面 |
| 下一轮验证 | 同一输入跑 N 次统计状态分布与费用；注入不同位置的失败看保留率；对比 template 与 llm 后端的素材引用准确率 |

实际用时与未完成部分见 `docs/timelog.md`。不把"计划做"写成"已实现"。
